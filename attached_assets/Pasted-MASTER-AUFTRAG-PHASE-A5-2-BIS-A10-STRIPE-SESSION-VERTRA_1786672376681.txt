PHASE A5.2 – SESSION-RESTORE NACH STRIPE
==================================================

ZIEL:
Nach erfolgreichem Stripe Checkout soll ein bereits eingeloggter Nutzer
direkt wieder in APH landen, ohne erneuten Login.

AUSGANGSPROBLEM:

Nach Checkout:
Stripe → success_url → APH

Nutzer landet zunächst auf Login-Seite.
Nach erneutem Login erscheint die Success-Meldung.

Serverseitige Session bleibt bestehen.

Prüfe vorhandene Logik:

CookieController
ath_sid
session_erstellen()
session_validieren()
st.session_state["user"]
st.session_state["_session_token"]
checkout Query-Param
SameSite
Secure
Path
Domain

1. COOKIE

ath_sid muss gesetzt werden mit:

secure=True
same_site="Lax"
path="/"

Falls installierte CookieController-Version path nicht unterstützt:
sicherer Fallback.

2. COOKIE-RESTORE

Wenn neue Streamlit-Session startet und "user" fehlt:

CookieController kann beim ersten Render noch None liefern.

Implementiere robust:

_COOKIE_MAX_WAIT = 4

- mehrere kontrollierte Reruns
- keine Endlosschleife
- Ladeanzeige während Cookie-Wartephase
- sobald ath_sid vorhanden:
  session_validieren()
  user + _session_token wiederherstellen
- bei ungültigem Cookie sofort Login
- nach maximalen Versuchen Login

3. CHECKOUT QUERY PARAM

?checkout=success oder ?checkout=cancel

darf keine Authentifizierung erzeugen.

Erst nach gültiger Session:
- Banner in session_state
- Query Param entfernen
- Success/Cancel-Meldung anzeigen

Ohne gültige Session:
- Login bleibt erforderlich

4. SESSION CLEANUP

Prüfe Mehrfachsessions.

Falls sinnvoll:
maximal z.B. 5 aktive Sessions pro Benutzer
älteste sauber deaktivieren.

Nicht alle Geräte pauschal abmelden.

5. TESTS

A:
Login → Reload → bleibt eingeloggt

B:
Login → externe Navigation → zurück → bleibt eingeloggt

C:
Login → ?checkout=success → Session wiederhergestellt → Success-Banner

D:
kein Cookie + ?checkout=success → keine Authentifizierung

E:
ungültiges Cookie → Login

F:
kein Endlos-Rerun

PHASE A5.3 – VERTRAGSANZEIGE / DATENQUELLE
==================================================

ZIEL:
"Mein Vertrag" muss die echten Stripe-/Mandantenwerte korrekt anzeigen.

Problem kann sein:

- BASIC statt TRAINER_BASIC
- Paketpreis fehlt
- Vertragsbeginn fehlt
- nächste Abbuchung / Verlängerung fehlt

1. FÜHRENDE DATENQUELLE

Prüfe, ob Vertragsseite aktuell teils aus benutzer, teils aus vereine liest.

Für Stripe-/Vertragsdaten muss führende Quelle sein:

vereine / technischer Mandant

Benutzer-Tabelle nur für:
- Login
- Profil
- personenbezogene Daten

2. PAKETNAME

Neue Stripe-Verträge anzeigen als:

TRAINER_BASIC
TRAINER_PRO
VEREIN_BASIC
VEREIN_PRO

Altwerte BASIC/PRO nur über normalize_lizenz_typ() kompatibel behandeln.

Keine pauschale Altbestandsmigration ohne Notwendigkeit.

3. PREISANZEIGE

Preis aus zentraler Paketdefinition ableiten:

lizenztyp + abo_intervall

Keine zweite Preistabelle neu erfinden.

Erwartungen:

TRAINER_BASIC monat → 9,99 € / Monat
TRAINER_BASIC jahr → 99 € / Jahr

TRAINER_PRO monat → 14,99 € / Monat
TRAINER_PRO jahr → 149 € / Jahr

VEREIN_BASIC monat → 24,99 € / Monat
VEREIN_BASIC jahr → 249 € / Jahr

VEREIN_PRO monat → 39,99 € / Monat
VEREIN_PRO jahr → 399 € / Jahr

4. VERTRAGSBEGINN

checkout.session.completed:

vertragsbeginn = COALESCE(vertragsbeginn, date('now'))

Nur setzen wenn noch leer.

5. NÄCHSTE ABBUCHUNG / VERLÄNGERUNG

Während Trial:

wenn subscription_current_period_end vorhanden:

"Erste Abbuchung am DD.MM.YYYY"

oder:

"Testphase endet am DD.MM.YYYY"

Bei aktivem Abo:

"Nächste Verlängerung am DD.MM.YYYY"

Bei gekündigtem Abo:

"Vertragsende am DD.MM.YYYY"

Kein künstliches Vertragsende setzen.

6. TEST

Mit einem lokalen passenden Testaccount:

monat
trial
stripe_customer_id vorhanden
stripe_subscription_id vorhanden

Erwartung:

Intervall = Monatlich

erste Abbuchung / nächste Verlängerung sichtbar
