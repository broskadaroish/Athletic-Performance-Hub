WICHTIG:
Produktivsystem.
Keine bestehenden Kunden, Benutzer, Vereine, Spieler, Tests, Trainingspläne,
Lizenzen, Stripe-Zuordnungen oder Rechnungsdaten löschen.

Keine Preise ändern.
Keine Stripe-Price-IDs ändern.
Keine Paketdefinitionen ändern.
Keine bestehende Checkout-/Subscription-/Webhook-Logik ersetzen.

ZUERST IST-ZUSTAND PRÜFEN, DANN MINIMAL UND KONSISTENT UMBAUEN.

8. BENUTZERVERWALTUNG ENTFLÄCHTEN
==================================================

Aktuelle Benutzerverwaltung zuerst prüfen.

Identifizieren:
- welche Funktionen gibt es ausschließlich dort?
- Rollen ändern?
- Benutzer anlegen?
- deaktivieren?
- Passwort?
- Vereinszuordnung?

Diese Funktionen sinnvoll verteilen:

Trainerfunktionen
→ Trainerportal

Vereinsadmin-Funktionen
→ Vereinsverwaltung

Globale Kontosperre
→ Superadmin

Erst wenn alle Funktionen übernommen sind:
separaten Menüpunkt „Benutzerverwaltung“ entfernen.

NICHT vorher löschen.

==================================================
9. ROLLENRECHTE
==================================================

SUPERADMIN:
- sieht alle Kunden
- alle Lizenzen
- alle Vereine
- alle Trainer
- globale Sperre
- Kundennummern
- Rechnungen
- Zahlungsstatus

VEREINSADMIN:
- nur eigener Verein
- Trainer verwalten
- Spieler verwalten
- Mannschaften
- Spielerzuweisungen
- Beitrittscode
- eigene Vertrags-/Rechnungsdaten sehen
- keine globalen Kunden

TRAINER:
- nur aktive Mandanten
- nur zugewiesene Mannschaften/Spieler
- Tests
- Trainingspläne
- Spieler bearbeiten
- keine Trainerverwaltung
- keine Rechnungen
- keine Lizenzverwaltung

==================================================
10. SPIELERMODELL – MODELL B
==================================================

Spieler gehören dem Kunden/Mandanten.

Verein:
→ Spieler gehören dem Verein

Einzeltrainer:
→ Spieler gehören dem Einzeltrainer-Mandanten

Trainer erhalten nur Zugriff.

Wenn Trainer Verein verlässt:
- Spieler bleiben beim Verein
- Tests bleiben
- Trainingspläne bleiben
- Historie bleibt
- nur Trainerzugriff entfernen

==================================================
11. TRAINER SIEHT NUR ZUGEWIESENE SPIELER
==================================================

Variante A verbindlich:

Normaler Vereinstrainer:
→ sieht nur explizit zugewiesene Spieler/Mannschaften.

Nicht zugewiesene Spieler:
→ nicht sichtbar.

Vereinsadmin:
→ sieht alle Spieler des eigenen Vereins.

Superadmin:
→ sieht alles.

==================================================
12. MEHRFACHMANDANTEN
==================================================

Ein Benutzerkonto = eine Person.

Ein Trainer kann:

- eigenen Einzeltrainer-Mandanten haben
- Verein A angehören
- Verein B angehören

Keine drei Benutzerkonten erzeugen.

Nach Login:
Arbeitsbereich/Mandant auswählen.

Beispiel:

Arbeitsbereich:
- Eigener Trainerbereich
- FC Musterstadt
- SV Beispiel

Alle Daten strikt nach aktivem Mandanten filtern.

==================================================
13. TRAINER-BEITRITTSCODE
==================================================

Wenn Trainer noch keinen APH-Account hat:
→ normales Beitrittsformular
→ Konto anlegen
→ E-Mail verifizieren
→ Vereinszuordnung pending
→ Vereinsadmin freischaltet

Wenn E-Mail bereits existiert:
KEIN zweites Konto anlegen.

Anzeige:

„Dieses Konto existiert bereits.
Bitte melde dich an, um dem Verein beizutreten.“

Nach Login:
→ neue Mandantenzuordnung anlegen

Keine neue Lizenz.
Keine neue Kundennummer.
Kein technischer Mandant.

==================================================
14. TRAINER VERLÄSST VEREIN
==================================================

Nicht Benutzer löschen.

Nur Mandantenzuordnung deaktivieren/entfernen.

Andere Mandanten bleiben erhalten.

Einzeltrainerbereich bleibt erhalten.

==================================================
15. KÜNDIGUNG
==================================================

Verein kündigt:
→ nur Vereinsmandant/Lizenz endet
→ Trainerkonten bleiben technisch bestehen
→ Zugriff auf diesen Mandanten endet
→ andere Mandanten bleiben aktiv

Einzeltrainer kündigt:
→ nur Einzeltrainer-Mandant endet
→ Vereinszugänge bleiben aktiv

Globale Benutzersperre:
→ nur Superadmin
→ sperrt gesamten Benutzer über alle Mandanten

16. RECHNUNGSMODUL
==================================================

Bestehende Tabellen/Funktionen verwenden:

rechnungen
rechnung_speichern()
rechnungen_laden()
rechnungsadressen
stripe_invoice_id

Kein zweites unabhängiges Rechnungssystem bauen.

Stripe Invoice bleibt Source of Truth.

Bei:

invoice.payment_succeeded

prüfen/ergänzen:

- Stripe Invoice ID
- Betrag
- Status bezahlt
- Rechnungsdatum
- Paket
- Leistungszeitraum
- Kunde/Mandant

→ idempotent in APH rechnungen speichern/aktualisieren

Bei:

invoice.payment_failed

→ Zahlungsstatus aktualisieren
→ Rechnung ggf. status fehlgeschlagen/offen aktualisieren

Doppelte Stripe-Events dürfen keine doppelten Rechnungen erzeugen.
